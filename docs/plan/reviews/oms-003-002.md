# Review: oms-003 / pass 002

## Findings

1. **P1 — blocking — Free orders still persist a crew-specific pre-flight warning.**
   - **Design contract:** `docs/plan/analysis/oms-entitlement-and-ux-blueprint.md`, *Product Rules* states that Free studios have no crew/resource suggestions; the approved user requirement is that crew must not be a concept in Free pre-/post-event workflow.
   - **Code:** `apps/web/src/actions/orders/orderCrudOperations.ts:101-108`, `apps/web/src/actions/leadActions.ts:330-336`, and `apps/web/src/actions/marketplaceActions.ts:484-490` call `performPreflightCheck` with `[]` members for Free. In `packages/domain/src/index.ts:103-105`, an empty member list generates the persisted warning `No active studio crew members match the required skills for this booking.` The Free OMS pre-flight panel can therefore still show crew terminology and a false crew conflict.
   - **Required fix:** For Free studios, create/use a pre-flight result that retains only non-ERP checks (date conflict and location) and omits resource/skill matching warnings and suggestions. ERP-enabled studios must retain the current full pre-flight behavior.

2. **P2 — non-blocking — tests exercise policy helpers but not the server action boundaries.**
   - **Design contract:** `docs/plan/tasks/oms-003.md`, *Verification* calls for Free crew-mutation rejection and owner-assignment behavior.
   - **Code:** `tests/backend-crud.test.ts:50-71` only tests pure helper outcomes. No action-level test proves that a Free request cannot persist a crew mutation.
   - **Required follow-up:** Add server-action contract tests where feasible after resolving the blocking Free pre-flight behavior.

## Conclusion

**blocked** — former crew-assignment bypasses are resolved, but the persisted Free pre-flight report still exposes the prohibited crew concept.
